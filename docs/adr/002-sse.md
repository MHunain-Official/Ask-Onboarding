# ADR 002: Server-Sent Events for streaming answers

**Status:** accepted

**Context.** Answers must stream token by token, with extra events (citations, ticket offer, errors).

**Decision.** `POST /api/chat/stream` returns SSE (`sse-starlette`). The browser reads it with `fetch` + `ReadableStream` and a small tested parser (`frontend/src/lib/sse.ts`), not `EventSource`.

**Why.**
- One-way server → client is all we need; SSE is simpler than WebSockets and works through ordinary HTTP proxies.
- `EventSource` cannot send a POST body or custom headers (we need the question and the CSRF header), hence `fetch`.
- Named events (`meta`, `token`, `citations`, `ticket_offer`, `done`, `error`) give the UI a clear contract.

**Consequences.**
- Proxies may buffer. In production Caddy routes `/api/*` straight to FastAPI with `flush_interval -1` instead of through the Next.js rewrite. Progressive delivery behind Caddy has **not** been verified on a real server yet.
- No resume after a dropped connection: a cut stream is saved as `partial` and Retry re-asks.
- The server generator only runs while its output is consumed; tests must drain the stream before asserting on its side effects.
